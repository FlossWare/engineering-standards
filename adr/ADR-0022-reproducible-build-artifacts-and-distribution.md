# ADR-0022: Reproducible Build Artifacts and Distribution

## Status
Proposed

## Date

2026-08-24

## Context

FlossWare components are increasingly consumed by applications, coding agents, setup tooling, and external environments. Installing directly from Git repositories can force consumers to clone source trees and build packages locally, increasing installation time, dependency on local build toolchains, and variability between environments.

FlossWare also needs a clear boundary between authoritative source and distributable artifacts. Configuration and source remain the basis for understanding and reproducing behavior; a wheel, source distribution, container image, or other release artifact is a derived delivery mechanism, not a second source of truth.

The ecosystem therefore needs a common build and distribution policy that supports convenient artifact-first installation without creating a hidden dependency on a particular package registry, operating system, build environment, provider, or pricing tier.

## Scope

Applies to FlossWare repositories that publish distributable software, including Python packages and other components for which release artifacts are produced.

## Non-goals

- Does not mandate a particular artifact registry.
- Does not require every repository to publish every artifact format.
- Does not prohibit source installation for development, debugging, unsupported environments, or explicit operator choice.
- Does not make generated artifacts authoritative over source or configuration.

## Decision

### Source and configuration remain authoritative

- Repository source and authoritative declarative configuration SHALL remain the source of truth.
- Generated release artifacts SHALL be reproducible from the corresponding source, dependency declarations, and authoritative configuration.
- Generated artifacts SHALL NOT be edited manually as a substitute for changing their source inputs.

### Artifact-first consumer distribution

- A released distributable component SHOULD provide a compatible prebuilt artifact for each supported consumer environment when practical.
- Consumer installation SHOULD prefer a compatible released artifact over building from source locally.
- Source builds MAY remain the fallback when no compatible artifact exists or when the operator explicitly requests source installation.
- Setup tooling SHALL make source fallback explicit and observable rather than silently presenting a source build as equivalent to an artifact installation.

### Python packages

For Python packages, repositories SHOULD publish standard Python distribution artifacts appropriate to the package, normally including a source distribution and a wheel when a wheel is meaningful for the package.

- Wheels SHALL be produced by CI/release automation rather than by consumer installation scripts.
- Package metadata SHALL declare supported Python versions and platform constraints accurately.
- A package SHALL NOT claim universal compatibility when its dependencies or compiled extensions impose platform constraints.
- Reproducible builds SHOULD use pinned or otherwise controlled build dependencies and deterministic release inputs where practical.

### Build and release automation

- Release artifacts SHALL be generated by automated CI or an equivalent repeatable release process.
- CI SHOULD validate that the artifact can be installed in a clean supported environment.
- Release automation SHOULD verify package metadata, artifact integrity, and basic import or smoke-test behavior before publication.
- A release SHOULD NOT be considered complete when the source tag exists but its required consumer artifacts failed to publish.

### Artifact provenance

Artifacts SHOULD retain sufficient provenance to identify the source repository and commit/tag, release/version, build workflow or environment, relevant dependency/build-tool versions, and integrity information such as checksums or registry-provided digests.

Where the ecosystem supports it, FlossWare SHOULD adopt signed artifacts or verifiable build provenance without making signing infrastructure a prerequisite for local development.

### Registry neutrality

Artifact publication SHALL remain independent of AI provider, model vendor, pricing tier, and execution topology.

A FlossWare installer MAY use a configured primary registry and documented fallback registries, but registry selection SHALL be deployment configuration rather than hidden business logic.

### Setup tooling

FlossWare setup tooling SHOULD follow this resolution order for released software:

1. Use a compatible released artifact.
2. If no compatible artifact exists, use an explicitly reported source fallback when supported.
3. If installation cannot proceed, report the missing artifact/platform compatibility issue rather than masking it with an unrelated local-build error.

Explicit source-install options MAY override this order for development and troubleshooting.

### Development installations

Developer workflows MAY continue to use editable installs and local source checkouts. Development convenience SHALL NOT dictate the consumer distribution model.

## Consequences

### Positive

- Faster and more predictable consumer installation.
- Less dependence on local compilers and build toolchains.
- Clear separation between source of truth and derived release artifacts.
- Consistent expectations across FlossWare repositories.
- Easier clean-environment and dogfood testing.
- Supports multiple artifact registries without architectural coupling.

### Negative

- Release pipelines become more important and require maintenance.
- Artifact publication adds CI/storage/release responsibilities.
- Platform-specific packages may require additional build matrices.
- Reproducibility and provenance require discipline and testing.

## Alternatives Considered

### Always build from Git at install time

Rejected as the default because it increases installation cost and environmental variability and unnecessarily requires local build tooling.

### Require a single package registry

Rejected because the distribution mechanism should remain replaceable and deployment-specific.

### Treat published artifacts as authoritative

Rejected because artifacts are derived outputs and can drift or become stale; source and configuration must remain authoritative.

### Artifact-first with explicit source fallback (chosen)

Provides convenient consumer installation while preserving development flexibility and the FlossWare configuration/source-of-truth model.
